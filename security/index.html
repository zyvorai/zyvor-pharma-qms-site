Security

What we built, and have not claimed.

Controls in the pilot product at v0.1.0, stated plainly, with the open items. Pilot, not validated, not 21 CFR Part 11 / Annex 11, synthetic data only. Not a penetration-test report and not an independent audit.

Strict mode: identity and sign-in

When the operator enables strict mode: Argon2id password login, optional TOTP second factor, passkeys (WebAuthn), OpenID Connect single sign-on (authorization code + PKCE), SAML 2.0 single sign-on, and SCIM 2.0 provisioning with its own token. Sessions are held server-side and re-checked on every request. Roles are local; SSO, SAML and SCIM can never grant admin. Passkeys, SAML and SCIM are flagged pilot.

Signatures and API keys

Batch QA approvals and document-revision approvals require password re-entry in strict mode and write a hash-chained e-signature record. API keys are stored hashed; a key can be pinned to a role and a site. Not a Part 11 / Annex 11 claim.

Login throttling

Password and passkey sign-in attempts are throttled per username: 10 failures in 15 minutes returns HTTP 429. State is in process memory, so it is single-node and resets on restart. A side effect is that someone can temporarily lock out a known username.

Outbound request guard

Connectors, webhooks, SAML metadata fetches and OIDC discovery go through an address guard that refuses loopback, private, link-local and similar targets by default, including after redirects and DNS rebinding. Operators with internal ERP / LIMS hosts must explicitly relax it.

Connector secrets

A connector secret is either encrypted at rest in the database under an operator-supplied key, or referenced by environment-variable name. Referenced names are restricted to a dedicated prefix so a connector cannot be pointed at arbitrary server settings. Secrets are not logged or returned by the API.

Tamper-evident audit

Application-level audit log in a verifiable hash chain, with review by exception (reviewed per site) and CSV export. Tamper-evident, not tamper-proof: the chain detects edits, not truncation of the newest rows, and the database owner can bypass the append-only rules. Restrict database privileges in deployment.

Site scoping (partial)

Records carry a site and users carry site grants; most record tables, workflow, notifications, AI drafts, API keys, webhooks and connectors are enforced. It is a pilot feature that has had no independent review. Honest gaps: documents, training assignments, the supplier master, the Schedule M checklist and market authorizations are shared across sites by design; audit events written before the site-scoping migration cannot be backfilled and are filtered best-effort; global connectors, API keys and the global email / webhook notifier are deployment-wide.

Read before exposing anything

Defaults and known gaps.

Default dev mode trusts identity headers

Out of the box the server runs in dev mode: it believes whoever the request headers say they are and defaults to admin. The shipped compose, Kubernetes and desktop launchers do not turn strict mode on. Never expose a dev-mode instance to anyone but yourself. Anything reachable by others needs strict mode; the server can be told to refuse to start otherwise (production flag), and refuses unknown mode values.

Role checks are inconsistent

Quality and laboratory decisions check roles, but many write endpoints (for example some market modules, cleaning, retains, packaging, stability pulls, release-checklist ticking, training and change creation, and the inspection kit download) have no per-role check, so a read-only user could call them. For any public demo, put a read-only guard in front; the live demo does exactly that.

Proxy and single-node limits

The API trusts the forwarded-for header, so run it behind a proxy that overwrites it. It has only been exercised as a single process; multi-replica operation is untested. Default database credentials in the shipped deployment files are demo values. TLS is yours to terminate.

AI-assisted security review, not an audit

An AI-assisted review (Claude) read the security-critical code and ran tests. It found and fixed issues, including an outbound-request weakness, connector secret exfiltration, dependency vulnerabilities, missing login throttling and a permissive cross-origin policy. It is not an independent audit or penetration test and certifies nothing. It did not cover the frontend source, the desktop app, deployment manifests, TLS, database role design or per-role authorization of every endpoint.

Open items

  • The SAML library has a known unfixed nil-pointer panic with no patched release; it is contained (the request fails, the process survives). We are tracking upstream.
  • Some dependency updates need a newer Go toolchain or major frontend upgrades that have not been applied (dev-server issues do not affect production builds).
  • Smaller open findings: password re-entry for signatures is not throttled, TOTP codes can be replayed within their window, SSO-only accounts can add a passkey without re-authenticating, SAML login state is not bound to the initiating browser, and a rare concurrent-signature race is suspected but unconfirmed.
  • No independent penetration test.
  • No SOC 2 / ISO 27001 / Part 11 certification.
  • Multi-site isolation has not been independently reviewed.
